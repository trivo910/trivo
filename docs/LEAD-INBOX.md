# Lead inbox

The hidden admin `/leads` inbox supports enquiry lists/details, search, filters, status/notes updates and filtered CSV export. It uses the existing glass components and native forms. Homepage audit/proposal forms and the contact form submit to `POST /enquiries`. Valid submissions are saved with New status, then redirect to `/thank-you`. Outbound replies and legacy form-entry import remain pending; no real enquiries are imported during development.

## Access and preservation

Policies require `leads.view` for list/details and both `leads.view` and `leads.manage` for updates/exports. Existing Admin/Super Admin permissions provide access; Editor and SEO Manager roles remain denied. Every write uses Form Request validation, verified admin sign-in sessions and CSRF. No manual lead creation or deletion route is exposed.

Follow-up updates accept only status, plain internal notes and the current `content_version`. Status options are New, In progress, Contacted, Qualified, Closed and Spam. Notes support multiline text up to 10,000 characters, without HTML/control payloads. The server sets `handled_by` to the authenticated account. Enquiry name/email/phone/company/service/message/source/tracking/IP fields are preserved. A row lock and optimistic version check reject stale saves; rejected forms retain their old version until reloaded.

Activity records contain generic update/export event codes and actor/record references, without enquiry contact data, notes or search values. Admin responses use no-store/private caching and noindex headers. Detail fields are escaped; source URLs are displayed as text rather than fetched or activated. IP hashes and tracking metadata are not displayed.

## Filters and CSV

Search matches name, email, phone or company. Status and exact service filters combine with inclusive UTC creation dates. Lists paginate 20 rows in descending ID order. Date bounds use the beginning of the first day and exclusive beginning of the day after the last day.

CSV export reuses validated filters and returns at most 1,000 matching records, newest first. The response identifies the limit and uses an attachment filename derived only from UTC time. Rows stream through a bounded cursor; output has a UTF-8 BOM and CSV quoting for commas, quotes and multiline fields. Standard formula prefixes, leading controls and whitespace-prefixed formulas are neutralized by an apostrophe prefix, including numeric-looking phone strings starting with plus/minus.

Exported columns are ID, name, email, phone, company, service, message, status, source URL and creation/update timestamps. Internal notes, handler IDs, tracking metadata and IP hashes are excluded. CSV downloads stay in ignored local QA storage during validation. Export activity records a request, not proof that the browser retained the downloaded file.

## Public submission and email delivery

Both homepage forms and the contact form use native POST submissions with CSRF, validation, a honeypot and a limit of three attempts per minute per IP. Validation errors retain the submitted fields. Contact messages are required; the shorter homepage forms do not require a message. Client-supplied statuses, notes and handler IDs are ignored. Source URLs are generated by the server and IPs are HMAC hashed.

Each saved enquiry creates two independent database queue jobs: a visitor thank-you and an admin notification. Both use the SMTP configuration in Admin ? Mail settings. Set **Enquiry notification email** to the receiving inbox; when blank, the configured **From email** receives notifications. Notification replies address the visitor. Thank-you messages contain a confirmation and reference number, without echoing the visitor's message. Email status appears on the lead details page. `sent` means accepted by SMTP, not confirmed inbox delivery.

Run `php artisan schedule:work` locally, or configure the production scheduler to execute `php artisan schedule:run` every minute. The existing schedule drains the database queue. For a one-off drain use `php artisan queue:work database --stop-when-empty --tries=1 --timeout=30`. Form emails always use this queue regardless of the test-email delivery setting. Configure SMTP before accepting live submissions. Failed email attempts remain visible on lead details; the lead remains saved. Jobs claim each log once to prevent duplicate sends when dispatched again; failed sends are not automatically retried because SMTP acceptance can be ambiguous.

`tests/Feature/PublicEnquiryTest.php` covers all three forms, inbox visibility, whitelisted persistence, input validation, spam/rate/CSRF checks, independent delivery logs, SMTP recipient fallback, duplicate job handling and escaped email content. Test messages use a fake mail transport.
